# 单场比赛赛后在线复盘版需求草案

日期：2026-10-19。状态：讨论稿，供需求确认和后续开发使用。

## 产品目标

提供一个固定的赛后复盘入口，由组织者控制当前展示哪场比赛以及旧比赛是否公开。运动员打开链接，就能查看当前比赛地图、组织者绘制的节点与连线、推荐路线，并通过 Route Builder 重建自己的跑法、比较路线选择、导出 GPX 用于后续视频制作。

服务部署在组织者自己的托管账号下，优先选择免费静态托管。地图展示、路线计算、个人路线编辑和文件导出均在浏览器内完成。

## 已确定需求与讨论假设

用户已提出的需求：

- 面向赛后运动员，在线访问。
- 优先保持分享链接不变，由组织者控制当前展示的比赛；旧比赛的开放策略可调整。
- 手机和电脑均支持，手机优先完成核心流程。
- GPX 优先兼容 QuickRoute、Headcam O 等轨迹分析与视频制作工具，仅服务地图版面对齐，不需要真实地理位置。
- 在现有软件内控制当前比赛和历史公开状态，不单独开发在线管理后台。
- 包含组织者已经画好的节点，以及自由探索路线选择的能力。
- 展示组织者提供的最好路线。
- 运动员能使用 Route Builder 画自己的路线，并导出 GPX。
- 部署在组织者控制的平台，优先免费，需要考虑中国大陆访问。

以下作为本稿建议，等待确认：

| 项目 | 建议默认值 |
| --- | --- |
| 旧比赛 | 由组织者逐场控制公开或归档，初始是否开放历史比赛待定 |
| 比赛范围 | 固定入口每次展示一场比赛、一套地图，可含多个组别或赛程及地图内多个楼层 |
| 访问方式 | 赛后公开，无需运动员登录 |
| 个人数据 | 只保存在当前浏览器或导出的本地文件中 |
| 发布操作 | 本地准备与预览，生成发布包，再部署到托管平台 |
| 界面语言 | 首版优先中文，复用现有英文界面时需同步补齐说明 |
| GPX 兼容版本 | 目标已确定为 QuickRoute 和 Headcam O，具体版本与样例待定 |

## 用户流程

### 组织者发布

1. 在现有软件中准备地图、节点、通行连线、楼层关系、控制点和赛程。
2. 选择公开的赛程，为各赛段指定推荐路线，可补充推荐理由。
3. 填写比赛名称、日期、简短说明及稳定的比赛标识。
4. 校验连通性、推荐路线有效性、地图资源和 GPX 的地图版面转换及时间信息。
5. 在本地以运动员视角预览，确认内容后生成静态发布包。
6. 在发布设置中指定当前比赛，并选择哪些历史比赛继续公开，部署到自己的托管账号。
7. 在目标设备和中国大陆网络上验收后，将固定入口链接发给运动员；后续换比赛继续使用该链接。

同一比赛更新时增加数据版本；不同比赛使用不同内部标识，即使共用入口也不混用个人路线。发布包应能整体备份、重新部署和回滚。

### 组织者控制发布状态

首版在现有软件提供发布设置，保存后重新生成并部署静态发布包。控制项包括当前比赛、每场历史比赛是否公开，以及暂停整个公开入口。暂停时显示“暂未开放比赛”。这些设置影响所有访问者，不能只修改组织者浏览器中的本地状态。

固定入口只显示当前比赛。历史比赛若开放，可以通过比赛专属链接访问；是否展示历史列表另行确认。归档比赛保留在组织者本地，发布时移除其公开数据和地图资源，并处理托管缓存。已下载的副本无法收回。

正在编辑路线的运动员遇到当前比赛切换时，页面继续绑定已加载的比赛标识，先保存草稿再提示重新进入；不得将旧路线挂到新地图。首版不要求实时推送切换消息。

### 运动员复盘

1. 打开链接，自动加载本场地图和默认赛程。
2. 选择自己的赛程或组别，再选择一个赛段。
3. 查看组织者推荐路线，探索其他可行路线并比较距离。
4. 进入“我的路线”，逐段选择经过的节点，重建自己的跑法。
5. 将个人路线与推荐路线叠加比较，修改并自动保存。
6. 导出 GPX，导入目标视频或轨迹软件。

## 首版功能

### 比赛与地图展示

- 首屏直接进入本场地图，显示比赛名称与赛程选择，无需手动导入文件。
- 展示地图、控制点、节点、边、楼层连接；节点与边可切换显示。
- 支持平移、缩放、适配整图和赛段定位。多楼层地图应能清楚识别上下楼关系。
- 公开地图、图结构、控制点和推荐路线为只读；运动员只编辑自己的路线。
- 发布站不提供赛事管理、图编辑、课程设置和任意比赛文件导入入口。
- 链接无效、数据损坏或加载失败时提供明确说明和重试入口。

### 路线探索与比较

- 按赛段查看推荐路线及有代表性的其他可行路线，支持叠加与单独显示。
- 显示路线距离、相对推荐路线的距离差；已有且适用的楼层切换指标可一起展示。
- “组织者推荐”由组织者指定；“最短距离”由算法计算，两种标记分别呈现。
- 预估时间若展示，须标明所用速度或模型；不可将最短距离直接称为实际最快路线。
- “自由探索”包括切换候选路线和指定经过节点。候选列表使用有界搜索，不承诺穷举所有可能路径。
- 搜索耗时较长时展示进度或忙碌状态，允许取消，不阻塞地图交互。
- 不连通、单向通行或非法楼层连接应明确提示，不能画出穿墙捷径。

### Route Builder

- 按选定赛程创建、命名、复制、删除多条个人路线。
- 逐段点击或触摸经过节点，沿合法图边补全路径；首版建议沿图构建，不加入任意手绘折线。
- 可增加、删除和修改途经节点，撤销和重做编辑；保留控制点顺序。
- 可与组织者推荐路线叠加比较，并清楚区分两者。
- 已编辑部分自动保存，刷新后恢复；缺失赛段应可识别。
- 路线无法完成时保留草稿，阻止误导性的“完整赛程”导出，并指出需要修复的赛段。
- 提供起跑时间、总用时或分段时间输入，为 QuickRoute 分析和 Headcam O 视频同步生成逐点时间，满足下一节要求。

### GPX 导出

GPX 的主要验收目标是路线能在 QuickRoute 和 Headcam O 中对齐比赛地图，并按时间正确播放。采用保留地图版面的合成坐标导出，实际 GPS 定位与地理校准不在需求范围内。GPX 格式仍需合法经纬度字段，但这些数值仅作为地图对齐载体。

| 项目 | 首版要求 |
| --- | --- |
| 导出对象 | 当前个人完整路线；推荐路线导出作为可选扩展 |
| 地图叠加模式 | 保留地图版面位置，以合法的合成经纬度承载路线形状，配套同一版面地图供目标软件对齐；标明为手工重建路线 |
| 楼层处理 | 保留并排楼层位置，检验楼层跳转时的轨迹播放。地图排版造成的跳转距离不得用于本站跑步距离统计 |
| 高程 | 有可靠楼层高度时写入；缺失时省略或按明确规则处理，不伪造实测高程 |
| 路径形状 | 保留实际路线几何与必要采样点，正确表达楼梯及合法转向 |
| 时间模式 | 支持目标软件需要的逐点时间；使用起跑时间和总用时或分段时间插值时，明确标记为估算 |
| 时间校验 | 正确处理时区、跨午夜、非递增输入和停留时间，采用目标软件接受的采样规则 |
| 文件有效性 | GPX 1.1 合法 XML，名称正确转义，经纬度合法，无空轨迹或无效数字 |
| 转换校验 | 地图版面转换须通过目标软件验证，保持方向与形状，不要求提供实际位置或真实地理校准 |

QuickRoute 官方说明支持 GPX 轨迹并将路线显示到地图图片上。[QuickRoute 官方介绍](https://www.matstroeng.se/quickroute/en/)。Headcam O 作者说明旧版使用 QuickRoute 对齐地图与轨迹，9.x 已加入路线编辑器，9.0 起不再要求依赖 QuickRoute。[Headcam O 下载与版本说明](https://wobelix.dk/download-headcam-orienteering-quickroute/)。因此不能将所有版本统一视作直接导入 GPX 的相同流程。

首版兼容验收包含：在 QuickRoute 中导入 GPX 并对齐地图；在选定 Headcam O 版本中，经该版本支持的直接导入或 QuickRoute 中间文件流程完成视频同步。提供同版面地图图片下载与简短操作说明；具体中间格式、采样间隔、楼层跳转及视频起点偏移处理，通过真实样例确定。合成地图坐标的兼容性尚未验证，开发前先做小样实验。

### 本地保存

- 官方发布数据作为只读基准，个人路线以增量数据保存并引用官方节点，不复制整套地图。
- 本地数据按比赛标识、发布版本和赛程隔离；两场比赛交替访问不会串数据。
- 发布版本更新后检查节点引用是否仍然有效；不兼容时保留旧草稿并提示，不能静默删除或错误套用。
- 提供个人路线文件备份与恢复，保留节点及编辑信息；GPX 负责互操作，不能代替完整草稿备份。
- 浏览器存储不可用或写入失败时提示，并允许导出当前草稿。说明清理浏览器数据会清除本地保存。
- 不增加账号系统、个人路线上传、追踪、分析埋点或用户数据收集。网站必要的静态资源下载与个人路线本地处理分开。

## 界面要求

地图占据主要空间，沿用深色主题、紫色选择色、Lucide 图标和紧凑工具栏。桌面使用固定工具栏与侧面板；手机使用可收起的底部面板，避免遮住路线。

图标按钮提供 tooltip、可访问名称和适合触摸的点击区域。主要操作配置快捷键，并与信息对话框、工具提示同步；手机操作不依赖键盘或悬停。

地图和路线使用共享 Canvas 渲染函数，设置 `user-select: none`。鼠标绘制及拖动事件按仓库约定阻止默认行为；触摸操作区分地图平移与节点选择。

信息对话框说明推荐路线的含义、构建路线方法、保存位置、GPX 条件和快捷键。首版以二维复盘为核心；三维展示、动画回放和直接视频导出列为后续增强候选。

## 发布与技术边界

建议采用“共用浏览器应用 + 每场只读比赛包”的结构。应用复用 `packages/core` 的路径搜索、路线模型、坐标转换和导出能力，以及共享渲染组件；公开模式使用独立的数据入口和个人路线状态。

托管平台仅提供静态文件，无需应用服务器或数据库。每场比赛包包含比赛元信息、版本、地图资源、图结构、赛程和推荐路线，并保留源数据的引用关系。路线结果若预计算，应记录对应数据版本和计算参数。

固定分享入口示例为 `https://站点域名/`，通过静态发布清单读取当前比赛标识。可选历史链接为 `https://站点域名/viewer/?event=比赛标识`，仅允许加载仍公开的比赛。入口清单需重新验证缓存，比赛资源按版本引用，避免新清单混用旧资源。要求直接访问和刷新有效，入口每次只加载一场比赛。首版不必为每场新建托管服务。

发布产物只包含组织者选定的公开比赛数据，不自动携带现有示例库、草稿或本地个人路线。脚本、字体、图标、地图及必要的 Worker 等资源随站点部署，减少外部域名依赖。

公开静态资源可被访问者下载。不将隐藏编辑按钮或复杂链接当作访问控制；若未来要求赛前保密或限制人员访问，应另行定义发布与认证方案。撤下站点不能收回已经下载的副本。

## 托管方案与中国大陆访问

平台资料核对日期：2026-10-19。部署前应再次核对实际账号额度。

| 候选 | 适配情况 | 需要确认的条件 |
| --- | --- | --- |
| Render Static Site | 适合现有静态导出，可使用 `onrender.com` 或自定义域名 | 免费部署有流量和构建额度，需测大陆实际访问 |
| Cloudflare Pages | 首选试部署平台，支持直接上传发布包 | 免费计划有构建与文件限制，需测大陆实际访问 |
| 其他静态托管或自有平台 | 同一发布包应可迁移 | 以访问测试、资源限制和实际成本决定 |

Render 官方提供免费静态站部署与自定义域名，但资源消耗计入工作区额度。[Render Static Sites](https://render.com/docs/static-sites)。当前文档列出 Hobby 每月 5 GB 出站流量；超额且绑定支付方式时收费，否则暂停工作区服务至下月。[Render 流量说明](https://render.com/docs/outbound-bandwidth)。因此首版应先测量比赛包大小，估算访问量。例如每次首次加载约 10 MB、500 次完整加载约为 5 GB，这只是忽略缓存、重复加载及其他流量的容量估算。

Cloudflare Pages 免费计划当前为每月 500 次构建、每站最多 20,000 个文件，单文件上限 25 MiB，大地图或内嵌地图的 JSON 要检查体积。[Pages 限制](https://developers.cloudflare.com/pages/platform/limits/)。Cloudflare 中国网络是 Enterprise 的独立订阅，不能把普通免费 Pages 等同于中国大陆节点服务。[China Network 接入说明](https://developers.cloudflare.com/china-network/get-started/)。

**部署决策建议：首选 Cloudflare Pages 试部署，Render 作为备选。正式选用以中国大陆目标网络测试通过为条件。** Cloudflare Pages 的静态资源请求免费且不限请求次数，符合地图下载和浏览器内计算的结构。[Pages 静态资源计费](https://developers.cloudflare.com/pages/functions/pricing/)。

首版由现有软件生成发布包，组织者通过 Cloudflare 控制台 Direct Upload 更新同一站点；拖放上传最多 1,000 个文件、单文件 25 MiB，超过文件数量时可使用 Wrangler 上传，最多 20,000 个文件。[Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)。发布设置在现有软件中完成，平台账号与上传凭证由部署工具管理，不进入公开站点产物。首版不承诺网页内一键上传。

可选自有域名作为长期固定入口，便于未来换托管而不换分享地址；域名注册通常需要单独付费，也不能保证大陆访问质量。大陆访问目前未实测，平台介绍不足以确认最终域名在各运营商的可用性。如免费候选不满足访问要求，再讨论低成本替代平台。

大陆验收应覆盖实际使用地区的移动、联通、电信网络，至少包含手机移动网络和家庭宽带，在不使用代理的情况下测试首开、完整地图加载、路线探索和 GPX 下载。分别记录冷缓存与再次访问结果，并测试最终分享域名。微信内置浏览器作为待确认渠道，若下载受限需提供打开系统浏览器的指引。

## 现有能力与开发差距

| 能力 | 当前代码依据 | 后续工作 |
| --- | --- | --- |
| 静态部署 | `apps/web/next.config.mjs` 已设置 `output: "export"` | 建立公开比赛入口和可迁移发布包 |
| 数据模型 | `packages/core/src/models/event.ts` 包含地图、图、赛程和自定义路线 | 定义发布元信息、版本和推荐路线引用 |
| 路线分析 | `apps/web/components/route-analysis/` 已有候选路线探索 | 裁剪运动员界面并明确推荐标记 |
| Route Builder | `apps/web/components/route-builder/` 已有沿节点构建、时间点和导出入口 | 实现只读官方数据与本地个人数据分离，适配触摸 |
| GPX | Route Builder 调用 `packages/core/src/io/gpx-generator.ts` | 当前固定使用斯德哥尔摩原点、高程为零，未写逐点时间；必须验证地图版面转换并补齐视频用途所需的逐点时间 |
| 其他 GPX 逻辑 | `packages/core/src/gpx-exporter.ts` 另有导出实现 | 梳理并复用公共转换逻辑，避免继续维护行为不一致的重复实现 |

现有 GPX 下载能力可作为入口复用，但不能直接作为地图对齐与视频兼容性已完成的依据。

## 首版验收标准

1. 从全新浏览器直接打开比赛链接，自动显示正确地图；刷新和分享后再次打开均有效。
2. 一场含多个赛程和楼层的真实样例可以正确切换，控制点和路径对齐地图。
3. 组织者推荐路线、算法最短路线和运动员路线可区分；比较距离使用同一计算规则。
4. 运动员能完成创建、修改、撤销、复制、保存与恢复路线；官方比赛数据保持不变。
5. 单向边、断开的节点和非法楼层跳转不能生成有效路线；相关错误可理解、可修复。
6. 两场比赛交替访问互不影响，比赛更新或存储失败不会静默丢弃个人草稿。
7. GPX 通过 XML 与坐标校验，在 QuickRoute 与选定版本 Headcam O 的完整流程中可用；路线方向、尺度、地图楼层位置和视频时间轴正确。
8. 无需真实地理校准即可导出地图版面路线，合成坐标在 GPX 合法范围内且标明用途；缺失赛段与无效时间提供具体提示。
9. 手机和桌面完成“打开比赛 → 探索路线 → 构建个人路线 → 下载 GPX”流程；桌面鼠标与触摸操作均无意外文字选择。
10. 中国大陆目标网络完成访问验收。建议性能目标为代表性比赛包在约定测试设备与网络上 10 秒内可操作，常规赛段切换 1 秒内反馈；正式阈值需结合真实包体积与图规模确定。
11. 网络检查确认个人路线和输入时间没有上传，应用未加入统计或追踪请求。
12. 同一入口从比赛 A 切到 B 后，首次访问和刷新均显示 B，个人路线仍按比赛隔离；已打开的 A 草稿不被错误迁移。
13. 组织者可控制旧比赛公开或归档；归档后其公开链接与数据资源停止提供。暂停入口有清晰提示，恢复及回滚有效。

开发测试应覆盖发布包解析、版本隔离、推荐路线引用、路线约束、坐标转换、时间插值、XML 转义和存储异常的 Vitest 单元测试，并使用真实比赛文件进行回归；核心运动员流程增加端到端测试。

2. 完成发布包规范、只读比赛加载与单场公开界面，验证候选托管平台的大陆访问。
